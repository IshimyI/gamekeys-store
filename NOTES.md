# NOTES

## Однократная выдача (в двух словах)

`node:sqlite` работает синхронно — каждый `.run()`/`.get()` выполняется целиком,
без пауз для event loop. Обработчики `POST /api/webhooks/payment` и
`POST /api/orders` написаны так, что от чтения заказа до записи нового статуса
нет ни одного `await`. Значит, пока Node обрабатывает один запрос, он физически
не может переключиться на другой посередине — даже если оба пришли "одновременно".
Это и есть вся защита от гонок, без ручных блокировок.

Дальше — несколько отдельных проверок, каждая под свой сценарий:

1. **event_id уникален** (`webhook_events.event_id` — PRIMARY KEY). Повторный
   вебхук с тем же event_id падает на `INSERT` — обработка не идёт дальше.
2. **Проверка статуса перед переходом.** Если по одному заказу пришло несколько
   разных event_id почти одновременно — первый переводит заказ в `delivering`,
   остальные видят уже другой статус и ничего не делают.
3. **Ключ забирается одним UPDATE**:

   ```sql
   UPDATE keys SET status = 'issued', issued_to_order_id = ?
   WHERE id = (SELECT id FROM keys WHERE status = 'available' LIMIT 1)
   ```

   Если `changes = 0` — ключей нет, это нормальный `out_of_stock`, не ошибка.

4. **У поставщика тоже есть защита от дублей.** Каждый запрос к поставщику имеет
   свой `request_id` (id заказа + имя поставщика). Если поставщик уже ответил —
   при повторном запросе просто отдаём тот же код, не спрашивая заново. Поэтому
   таймаут не значит "не получилось": запрос может ещё выполняться в фоне, и
   если поставщик всё-таки ответит успехом, заказ доставится этим ответом —
   без второго обращения и без второго ключа.

Если когда-нибудь появится больше одного процесса, пишущего в один файл БД —
SQLite сам сериализует запись (включён WAL). Но основная защита — именно
однопоточность Node, а не это.

## Промокоды

Скидку всегда считает сервер, с клиента приходит только код. Лимит проверяется
одним запросом:

```sql
UPDATE promo_codes SET used_count = used_count + 1
WHERE code = ? AND used_count < max_uses
```

Если `changes = 0` — лимит исчерпан, заказ не создаётся.

## Почему `node:sqlite`, а не `better-sqlite3`

Начинал с `better-sqlite3`, но на Node 23 / arm64 (macOS) он падал с сегфолтом
даже после пересборки. Перешёл на встроенный в Node 22.5+ `node:sqlite` — та же
синхронность, на которой всё держится, но без нативной сборки вообще. Минус —
модуль пока экспериментальный.

## Что упростил осознанно

- Хранилище — файл SQLite, не Postgres/Redis. Для одного процесса и задачи на
  корректность этого достаточно, и в условии так и разрешено.
- Оплаты нет — фронт сам дёргает вебхук сразу после создания заказа.
- Пул ключей общий, не привязан к конкретному товару — для проверки на гонки
  это не важно.
- Админка — только эндпоинты, без интерфейса, как и просили.
